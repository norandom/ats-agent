# Check retirement prerequisites

Keep the legacy application until the selected replacement candidate has passed actual installed acceptance. These maintenance checks read files and Git objects. They never remove or restore a file, call WordCraft, publish a package or grant mutation authority. Task 7.1 owns the eventual tracked change.

`release/retirement.json` declares the eight tracked application files to remove and the five documentation files to update. The code checks this exact inventory against the approved policy. A JSON approval flag cannot expand it. The project README already follows the adopter workflow and requires no retirement edit. Current Dagger and CI use Node tooling; external deterministic tools may still use Python internally.

Create a private, independently selected attempt under ignored outputs or outside the repository. Version 1.1 contains `schema_version`, `kind: retirement-attempt`, `phase`, `plan_sha256`, `source_a`, `recovery_revision`, `retirement_revision`, `source_b` and `dedicated_diff_sha256`. Before removal, the last three fields are null and `recovery_revision` is the current pre-removal HEAD. After removal, retain that recovery revision, the dedicated retirement commit, its binary diff digest and the fresh B source revision. No build-generated artifact or approval belongs in the tracked declaration.

The gate rechecks the current A readiness selections, including actual installed evidence, all eight readiness gates and pinned reviews. It compares the current generic Git blob path, size and hash inventory with A's prepared snapshot. Regular, non-executable Markdown/JSON metadata in `.kiro/specs/portable-skill-release/` may follow A. Other changed paths must belong to the generic closure or exact policy inventory; new code outside that closure fails. All eight legacy files must still match A's tracked Git objects before removal. A conservative screen rejects any legacy module-name token in retained tracked Python, including comma, multiline or dynamic imports. Ambiguous mentions also require ownership review; the screen does not prove Python import semantics. Payload bytes must match exactly; maintenance checkout line endings may differ.

After removal, require a dedicated commit whose parent is the retained pre-removal revision. Its diff must contain exactly eight deletions and five documentation modifications. No ignored private inputs, supplied references, output files, user `.env`, documents or backups enter the operation. Keep the prior revision and exact diff for recovery. If B fails, report retirement incomplete; restore only the dedicated approved paths or revert that dedicated change. Never reset unrelated work or rewrite published history.

B requires its own source identity, artifacts, installation, current host evidence, owner regressions and competent reviews. A's receipts cannot become B's receipts because package content looks similar. Only fresh passing B acceptance supports completion. The operator must authenticate reviewers, actual observations and the authorized task; hashes cannot establish semantic truth.

Use `pnpm.exe run release:retirement ABSOLUTE_PRIVATE_SELECTION.json` in PowerShell, or `pnpm run release:retirement /absolute/private-selection.json` in Bash. The selection contains `plan` (absolute path plus independently selected `expected_sha256`), `acceptedCandidate` (`readiness` with the five current readiness selectors, and `validation` selecting the pinned completed candidate-A validation report) and `currentSource` (`root`, full `currentRevision`, pinned `attempt`, and `candidateB`, null before removal). A completed validation report must contain the exact mandatory suite/owner execution counts, current evidence bindings and unchanged log digests. An imported ready flag cannot replace this evidence. The API reference in `retirement.cjs` defines the current selection contract. A missing or failed prerequisite leaves execution unassessed.

## Complete validation

`pnpm.exe run release:validate ABSOLUTE_SELECTION.json` in PowerShell, or `pnpm run release:validate /absolute/selection.json` in Bash, runs the fixed inventory in `tests/portable-skill-release/validation-manifest.json`. The selection identifies `schema_version: 1.0`, `kind: release-validation-selection`, `mode`, immutable `source` (`root`, full `sourceRevision`, numeric `sourceEpoch`), separate writable `work_root`, fresh `run_id`, absent absolute `output`, and `acceptance`.

Generic mode sets `acceptance` to null. It verifies the immutable prepared descriptor, executes every declared deterministic suite and measures TAP totals. Zero tests, any failure, cancellation, pending test or mandatory skip fails the run. The 44 criteria remain unassessed for actual acceptance. CI may succeed in this mode without release readiness or a desktop support claim.

Candidate A and B modes run on the selected Windows host. They require independently pinned current readiness selections, a criterion review and explicit owner inputs. The five existing version-specific validators retain their own algorithms and evidence rules. The session validator needs its actual report, session and fresh external output directory; documents need their actual receipt and review; refinement needs its immutable index, expected normalized digest and independent selection review. Missing host inputs block acceptance. No simulated receipt substitutes for actual observations.

The criterion review binds the current source, build input digest, exact archive digests, installed index digests and host/connection identities. Every criterion is represented. Reviews reference exact files from the selected installed evidence; competent human review remains necessary. Owner inputs must also belong to that reviewed evidence closure. Candidate A establishes the prerequisites for later retirement. Its fixed policy leaves 7.3, 7.5 and 7.6 unassessed, with observation class `control`, empty references and the reason `Deferred until task 7.1 and fresh B acceptance.` All other A criteria require current review. Candidate B requires passing current evidence for all 44 criteria and a pinned post-removal retirement selection. Validation reports and private logs stay outside the six-file distribution directory.
